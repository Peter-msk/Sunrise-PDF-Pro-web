# Sunrise PDF PRO Web R40-DEV2 — 글자·도형 보존 우선 수정

기준: 사용자 지적에 따른 R40-DEV1 후속 개발. 기준 소스: `Peter-msk/Sunrise-PDF-Pro-web` main `c26a64b5bff6ff465fbdfd148a78d13a89a2df67` + R40-DEV1 로컬 통합. 운영 반영 없음.

## 왜 변경했는가

한글 COM을 기준으로 글자·표·도면을 보존하기 위해 rhwp를 쓰기로 한 요구에 어긋나게 이미지형 PDF가 기본이었고, 전문 출력 실패 시 전체 또는 일부 페이지가 이미지로 자동 대체됐다. 기존 성공 기록은 이미지형 출력에 대한 결과이며 글자 보존 성공 증거가 아니다.

rhwp는 한컴 COM과 다른 오픈소스 구현이다. COM과 동일한 결과를 목표로 하나 자동으로 동일해지지 않으며 비교 전 동일 품질을 보장하지 않는다.

## 변경 사항

1. 웹 UI, 초기화 및 API의 기본 엔진을 `professional`로 변경했다.
2. 기본 엔진은 rhwp의 `renderPageSvgWithProfile(page, 'print')`를 사용하고 SVG의 글자·도형을 PDF 객체로 옮기는 경로를 시도한다.
3. 지원할 수 없는 폰트 또는 SVG 페이지는 오류로 종료하고 작성 중인 PDF를 폐기한다. 이미지로 자동 재시도하거나 해당 페이지만 이미지화하지 않는다. 이미지 출력은 사용자가 별도로 선택해야 한다.
4. 글꼴 불일치 오류에 필요한 폰트 패밀리 및 굵기/스타일을 포함해 원인 추적을 돕는다. 글자 내용 자체는 오류에 포함하지 않는다.
5. 인쇄 경로의 혼합 크기 용지에 대한 자동 이미지 대체도 기본적으로 차단했다. 인쇄 미리보기/표시용 이미지 생성과 PDF 페이지 자체를 이미지로 저장하는 것은 다르다.
6. Worker의 기본 출력 정보와 UI, 기존 이미지 호환 경로의 검증 스크립트를 새 기본값에 맞췄다.

## 기술 선택과 다음 우선순위

- 설치된 `@rhwp/core@0.8.7`의 공개 TypeScript 정의에는 SVG 렌더링 API가 있으며 직접 PDF로 내보내는 공개 메서드는 확인되지 않는다.
- rhwp CLI에는 `export-pdf`가 존재하지만, 브라우저에서 직접 실행할 수 있다고 검증되지 않았다. WASM 노출/자체 빌드 또는 사용자 문서를 처리할 서버 등 실제 실행 경로를 비교해야 한다. 문서의 처리 위치·개인정보 경계와 운영 인프라도 함께 결정해야 한다.
- 공식 HWP 예제에서 발견된 실제 폰트 계열과 사용 가능한 라이선스/글리프·서체 변형을 조사하고, 정확한 글꼴 매칭을 우선한다. 불가피한 대체는 명확히 표시하고 기준 출력과 비교한다.
- 형식/폰트 부재 및 복잡한 SVG에서 글자·그림이 누락되거나 실패하지 않는지 실문서로 보완한다.
- 동일한 원본 HWP/HWPX의 한컴 COM PDF와 비교해 폰트·줄바꿈·표·도면·용지·페이지 수·PDF 텍스트 추출을 확인한다.

현재 수정은 잘못된 자동 이미지 성공 판정을 제거한 **중간 개발 단계**다. 한컴 품질이나 무수동 HWP→텍스트 PDF 변환을 완성했다고 표시하지 않는다.

## 공식 rhwp 0.8.7 실제 PDF 내보내기 추가 검증

2026-11-06에 공식 Linux x86_64 rhwp 0.8.7 릴리스 아카이브의 SHA-256 `f1e541a25cfe76b6bc1daf18bf9c1f9a5ac5e03e2c01b188daaf54107214f631`를 확인하고 로컬에서 실행했다. 서로 다른 공식 HWP/HWPX 예제 2개를 사용했으며 모두 1쪽이다.

글꼴이 없는 환경에서 SVG PDF backend로 출력하면 두 문서의 PDF에서 추출되는 글자가 0자였다. 명령 자체가 exit 0을 반환했더라도 결과물 품질은 실패다.

NanumMyeongjo/NanumGothic TTF 및 일반/굵게 글꼴을 별도의 시험용 경로로 제공하고 `--backend svg --profile print --fallback-serif NanumMyeongjo --fallback-sans NanumGothic --fallback-mono NanumGothic`를 사용한 결과:

| 항목 | HWP 예제 | HWPX 예제 |
|---|---:|---:|
| 출력 PDF | 8,604 bytes | 7,723 bytes |
| 입력 문서 텍스트의 공백 제외 글자 수 | 100 | 17 |
| PDF 추출 텍스트의 공백 제외 글자 수 | 100 | 17 |
| 공백 제거 후 입력·PDF 문자열 일치 | 일치 | 일치 |
| 추출된 한글 음절 | 100 | 0 (영문 예제) |
| 페이지 이미지 객체 | 0 | 0 |
| 임베디드 폰트 | NanumMyeongjo, subset, ToUnicode | NanumMyeongjo, subset, ToUnicode |

HWP 페이지의 PDF 렌더링에서도 한글이 보이는 것을 확인했다. 두 예제의 모든 글자가 일치했다는 결과는 이 두 단일 페이지에 한정된다. Nanum은 원본 한컴 폰트와 다른 대체 폰트이므로 실제 한컴 COM 출력과 같은 글꼴·줄바꿈·표·도면 품질이 확인된 것은 아니다.

반면 `--backend direct` 시험은 글꼴 경로를 주어도 HWP 예제에서 0자가 추출됐고, 이 버전은 SVG backend의 `--fallback-*` 옵션과 함께 사용할 수도 없었다. direct backend를 검증 없이 기본으로 정하지 않는다. 이 결과는 rhwp 공식 CLI의 로컬 실행이며 `@rhwp/core` 브라우저 WASM의 PDF API 연결이나 웹 서비스 실기 성공을 의미하지 않는다.

생성한 예제 PDF와 원본 예제, 공개 글꼴 라이선스는 별도 `Rhwp_Vector_Examples.zip`에 담았다. 개발 코드·바이너리·글꼴을 자동 배포하지 않았다.
